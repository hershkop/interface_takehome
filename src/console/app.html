Record a new capability

How recording works, and how to write a goal it can follow
  1. A model drives the live app in a browser window you can watch. It takes one action per turn and re-reads the screen in between, so it is never deciding a second move from a page it has not seen. Every action is checked against the policy before it runs — an origin outside the allowlist or a control that looks irreversible is refused mid-run.
  2. You write the goal in plain language, naming concrete values: “Log in, then look up account 12678 and read its balance and account type.” Vague goals wander and hit the step limit. Say where to start, what to do, and what to read at the end.
  3. Values you list as inputs get parameterised. Put accountId=12678 in the inputs field and the recorded artifact takes accountId as an argument instead of hard-coding 12678 — including where that value appears inside a locator or a condition, not just in a typed value.
  4. What you get back is a draft: a step list with ordered locator candidates, typed outputs, and no handlers. That is deliberate — a single happy-path run cannot know how the application reports “no such record”, and inventing handlers would be fiction.
  5. Then review it. On the Capabilities tab, read the steps, add the handlers for the paths the run never took, leave a note saying what you checked, and promote it to approved. A draft is hidden from the agent-facing catalog until you do — a draft an agent can see is a draft it will call.

Needs ANTHROPIC_API_KEY in .env, the target app reachable, and its origin allowed by the policy. A run costs real tokens; the Audit tab shows what each one came to.
